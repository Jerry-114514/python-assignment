# 珞珈骑迹方案可行性评审
日期：2026-11-03
评审对象：01-选题与实施方案.md v1.0。本文是评审意见，未执行方案中的下载、开发或部署指令。未取得课程原始任务书，课程要求与截止日期尚待确认。

## 结论
有条件可行，建议立项前修改。公开数据上的借还量预测、可视化、规则建议适合课程项目；原方案对真实库存、空车概率、等待时间及武汉本地适用性的承诺超出了现有数据的支持范围。
5–6 人每周 6–8 小时、8 周约为 240–384 人时，包含学习、集成、报告与个人实验后，完整五页系统及全部高级功能风险较高。以下建议是工程判断，尚未下载数据或跑基准实验。

## 必须修改的问题

### 1. 借还流量不能直接给出库存和空车概率
Citi Bike 行程数据列出了借还时间、站点、坐标等，不包含完整历史库存与调度记录。官方将行程数据与实时 GBFS 分开发布。仅有借还量与容量不能推出当前车辆数或空车概率。
库存关系应为：下一时刻库存 = 当前库存 + 还车 - 借车 + 人工调度及其他修正。还需考虑有效容量、故障及停运。已发生借还量属于受供给限制的成交量，并非未被满足的全部需求。
修订：必做目标改为“借还流量与净流入压力”；无库存时删除真实空车概率及分钟级等待承诺。调度页使用显式输入的库存与容量做模拟，清楚标明假设。即便有期望库存，输出概率还需要不确定性模型与校准。
参考：https://citibikenyc.com/system-data

### 2. 武汉无桩场景与海外有桩数据需要分开
无桩共享单车适合使用“停车区域/电子围栏/可用车辆”，不能直接照搬“满桩无法归还”。是否存在特定本地容量限制需实地核实。
纽约模型不能换上武汉站名就当成本地预测。若选 Citi Bike，必须配纽约天气、America/New_York 时区及当地日历，并处理夏令时；不能配武汉天气与中国节假日。
修订：真实评测在来源城市完成；武汉页使用独立的示例或模拟数据并标识。18 个观测时段和便利问卷只支持探索性对比，不能证明模型可以迁移。

### 3. 未来 24–168 小时的推理逻辑尚未定义
在出发时刻一次预测未来一天时，第二小时起的 lag_1h、短期 rolling 等真实输入不可得。直接对整个测试期预先计算这些特征，可能只评估了逐小时更新的一步预测，不能证明一次输出七天的能力。
修订：首版只做“每小时更新的下一小时预测”。24 小时预测作为扩展，明确递归预测或按 horizon 的直接模型，并按多个预测起点做回测。未来天气需使用当时可获得的预报；事后历史天气只能标为已知天气条件下的回测。
参考：https://open-meteo.com/en/docs/historical-weather-api

### 4. 防泄漏示例本身有错误
原文 groupby().shift(1).rolling(24) 中 rolling 已脱离分组，会跨站点累计。先按站点时间排序、补齐有效运营期间的小时面板，再使用：
```python
panel = panel.sort_values(["station", "hour_ts"])
panel["roll_24h"] = panel.groupby("station")["borrow_cnt"].transform(
    lambda s: s.shift(1).rolling(24, min_periods=6).mean()
)
```
补零要区分“确认没有行程”和“源文件缺失/站点未运营”，不能一律视为零。
TimeSeriesSplit 的 gap=24 是 24 行样本，不是 24 小时。多站点面板应按唯一小时生成折，再映射到所有站点，确保同一小时不会跨训练与验证；gap 根据预测跨度及标签覆盖区间确定。
站点 Top-N 及均值基线必须仅用训练期确定。主模型应加入站点标识或充分的站点特征，否则难以区分不同站点。
参考：https://pandas.pydata.org/docs/reference/groupby.html
参考：https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html

### 5. 路线、建议与减排缺少可验证输入
经纬度直线距离不能当作真实步行/骑行路线；地铁还需线路、换乘、票价与候车假设。
修订：预设 3–5 组起终点，使用人工核验路线与标明的固定耗时；候选不足 3 个时如实返回。
小时模型不能支撑精确到 15 分钟的差异，提前出发对比改成小时级情景比较；没有因果识别时不要称作已验证的因果收益。
碳排统一距离、载客率和核算边界，注明系数来源；“比驾车少排放”是指定基准下的估算，不能把所有建议累加为实际减排。删除固定“一棵树每天固碳”的换算。
调度需维护车辆载荷、站点库存/容量、供给来源和未满足量；位置改变后按距离计算的优先级需要重算。没有时间窗时不应直接把问题定义为 VRPTW。

## 推荐首版范围
| 模块 | 必做 | 延后 |
|---|---|---|
| 数据 | 单一来源城市、20–50 站、连续 3–6 个月；先用 1 月验证读取 | 200 站及多数据源适配 |
| 预测 | 下一小时借车量；季节基线与一个 HistGBR | 还车量、24 小时及七天预测区间 |
| 展示 | 总览/预测评估/规则建议三个页面 | 五页完整产品 |
| 建议 | 预设路线、透明打分、小时级情景比较 | 任意起终点及等待时间概率 |
| 调度 | 给定库存的 5–10 站模拟，标明假设 | 真实运维优化 |
| 本地验证 | 少量实地观测用于描述场景差异 | 本地预测准确性与迁移证明 |

保留调度小演示有助于体现数据结构课程中的字典、优先队列、图和复杂度分析，不需要把整个产品做完。

## 排期与验收调整
- 第 1 周：核实课程任务与截止时间，下载一个月并检查实际压缩包结构、字段、许可及资源占用；现代月包可能有多个 CSV，不能假定单文件或固定体积。
- 第 2 周：完成分块读取和面板、数据字典与缺失记录。
- 第 3 周：完成基线和按小时划分的回测，验证滚动窗口不跨站点、同一小时不跨折。
- 第 4 周：主模型与分组误差分析。提升 15% 和 WAPE≤0.35 作为探索目标，不能承诺；WAPE 分母为零须单独处理。
- 第 5–6 周：三个页面和规则建议；主链路稳定后才加入库存调度模拟。
- 第 7–8 周：联调、报告、汇报、离线演示，保留至少一周缓冲。

验收重点：可复现、无未来信息、基线公平、假设透明、演示稳定。打不过周周期基线不必然是代码错误，应如实分析数据和任务。

## 其他工程修订
- src 布局需增加 pyproject.toml 并 pip install -e .，或提供明确的路径配置，否则 python -m luojia_ride.data 不保证可用。
- requirements 中 ==2.2.* 等是小版本范围，不能称为完全锁定；确定 Python 版本并记录实际成功安装的依赖。
- Streamlit 可对 DataFrame 做缓存哈希；“传 DataFrame 会导致缓存失效”的表述不准确，应关注哈希开销与实际缓存键。
- net_flow 建议由两个预测量相减，避免三个独立模型互相矛盾。
- 预测辆数的区间不能直接写成等待分钟区间。
- 数据原始包不上传 GitHub。小样例是否能公开需按具体许可判断；公开仓库内不放个人信息。

最终建议：保留选题与轻量技术栈，以“公开数据的流量预测 + 透明规则建议 + 可选库存调度模拟”立项。原版完整功能作为扩展路线，不能原样作为 8 周必交承诺。
